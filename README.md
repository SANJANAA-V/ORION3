# ORION³: pre-payment risk scoring for authorized payment scams

**Live demo:** https://orion3.streamlit.app  
**Status:** research prototype. Trained and tested on simulated payment data plus public benchmark datasets. It is not connected to any bank or UPI system and must not be used for real payment decisions.

## The problem

In authorized payment scams (fake KYC calls, fake prizes, fake customer care, remote-access tricks) the victim approves the payment themselves. Ordinary "unauthorized transaction" fraud models do not target this case, and money sent by UPI is hard to recover. ORION³ explores scoring a payment **before it completes**.

## What it does

For one payment, ORION³ combines three signals and returns **ALLOW, WARN or BLOCK** with a plain-language reason.

| Signal | What it looks at |
|---|---|
| Sender behaviour | Amount compared with the sender's usual payments, first payment to this receiver, time of day |
| Receiver network | How many different people paid the receiver in the last hour, whether it already passed money on, account age |
| Message | Whether the message that led to the payment resembles scam wording (TF-IDF + logistic regression) |

A logistic-regression fusion layer combines the three scores. Warn and block thresholds are chosen on validation data. The reasons come from the fusion model's own weights.

## Results

### A. Real public data (benchmarks of individual methods)

**IEEE-CIS Fraud Detection** (590,540 card transactions, 3.50% fraud). Chronological split by transaction time: 413,378 train / 88,581 validation / 88,581 final holdout. Same 58 features for every model. Generated by `ieee_cis_benchmark.py`.

| Model | Validation PR-AUC | Validation ROC-AUC | Final holdout PR-AUC | Final holdout ROC-AUC |
|---|---|---|---|---|
| Dummy (base rate) | 0.034 | 0.500 | 0.035 | 0.500 |
| Logistic regression | 0.319 | 0.834 | 0.281 | 0.831 |
| Decision tree | 0.369 | 0.826 | 0.379 | 0.822 |
| **LightGBM** | **0.557** | **0.912** | **0.502** | **0.900** |

- LightGBM final holdout PR-AUC 0.502 (95% bootstrap CI 0.483 to 0.522). The holdout was scored once, after all choices were made on validation.
- Operating point: the threshold giving 1% false positives on validation (0.219) gave recall 0.449, precision 0.538 and a false-positive rate of **1.39%** on the later holdout, so thresholds drift as the data changes over time.
- Feature-group ablation (validation PR-AUC, mean of 3 seeds, full model 0.552):

| Removed group | PR-AUC | Change | Effect |
|---|---|---|---|
| C features (count features) | 0.396 | -0.156 | clear |
| Card attributes | 0.515 | -0.037 | clear |
| Address and distance | 0.541 | -0.011 | clear, small |
| M features | 0.542 | -0.011 | clear, small |
| D features | 0.543 | -0.010 | within noise |
| Time and amount | 0.545 | -0.008 | within noise |
| V features | 0.551 | -0.001 | within noise |

**UCI SMS Spam Collection** (5,169 messages, random 75/25 split in the notebook): TF-IDF + logistic regression, PR-AUC 0.966, ROC-AUC 0.990. This is general spam, **not** payment-scam detection.

IEEE-CIS is credit-card transaction fraud, not UPI and not authorized-payment scams. These numbers show that the methods work on real data. They do not show that ORION³ catches real UPI scams. The 12-threshold table is in `results/ieee_thresholds_validation.csv` when you run the script.

### A2. Message models tested on real messages written by other people (`text_real_eval.py`)

Real smishing: 11,080 English messages from the "Fishing for Smishing" dataset (Agarwal, Papasavva, Suarez-Tangil, Vasek, ACM IMC 2025, CC BY 4.0), of which 1,943 came from Indian networks. Generic "spam" and "others" types were left out. Real legitimate SMS: 1,130 held-out "ham" messages from the UCI SMS Spam Collection. Threshold 0.5. PR-AUC is not reported because scam and legitimate messages come from different sources and years.

| Message model | Recall, all smishing | Recall, Indian-network smishing | False alarms on real legitimate SMS |
|---|---|---|---|
| Demo model (trained only on simulated template messages) | 0.681 | 0.827 | **0.388** |
| TF-IDF + logistic regression trained on UCI SMS Spam | 0.662 | 0.869 | 0.013 (same source as its training data, so optimistic) |

Recall by scam type (demo model / UCI model): banking 0.68 / 0.71, delivery 0.70 / 0.47, government 0.62 / 0.59, telecom 0.76 / 0.79, wrong number 0.48 / 0.05.

What this shows: the demo's message model, learned from a few fixed templates, finds most real smishing but also flags 39% of real legitimate SMS, so its standalone score cannot be trusted. In spot checks, the fused demo mostly ignores moderate message scores, so ordinary messages are allowed but some real scam wording is too. No public dataset of real legitimate bank and UPI notifications was found, so false alarms on those are untested.

### B. Simulated UPI-style system (tests the three-signal design end to end)

Test PR-AUC on a time-ordered held-out period. "Hard" mode uses low-and-slow campaigns, smaller scam amounts, fewer messages, more legitimate bursts and more alarming-looking legitimate messages.

| Model | Easy | Hard |
|---|---|---|
| Rules (hand-set weights) | 0.500 | 0.044 |
| Message only | 0.549 | 0.459 |
| Sender behaviour only | 0.454 | 0.192 |
| Receiver network only | 0.824 | 0.366 |
| Behaviour + network | 0.946 | 0.556 |
| **Fusion (all three)** | **0.968** (95% CI 0.951 to 0.982) | **0.788** (95% CI 0.731 to 0.842) |

- Held-out scam family ("impersonation", never seen in training): fusion PR-AUC 0.948 (easy), 0.652 (hard).
- Payments with no message at all: PR-AUC 0.939 (easy), 0.577 (hard).
- Legitimate fundraiser-style bursts wrongly flagged: 0.9% (easy), 0.5% (hard).
- Thresholds are chosen on validation data (about 1% false-positive rate for WARN), then applied to the test period.

### C. Serving speed

FastAPI endpoint, 300 HTTP requests on a Kaggle notebook (local network, models only, receiver and sender statistics supplied in the request): **p50 11.4 ms, p95 13.3 ms, p99 14.5 ms**. A real deployment would also need time to look up those statistics.

## What is real and what is simulated

| Part | Real data | Simulated |
|---|---|---|
| LightGBM benchmark, baselines, ablation and thresholds (IEEE-CIS) | yes | no |
| SMS spam baseline (UCI) | yes | no |
| Simulator, fusion model, live demo, API | no | **yes** |
| Scam messages in the simulator | no | **yes**, generated from a few fixed templates |

## How the simulator avoids testing itself

An earlier version generated features directly from the label, so models only learned the generator. The current version (`orion3_sim_v3.py`) generates payments and scam campaigns as events and then **computes every feature in time order from past events only**. It includes legitimate fundraiser bursts, alarming-looking legitimate bank messages, large legitimate payments to new people, and scam campaigns that forward money through mule accounts. The test period contains a scam family that is never seen in training. A hard mode checks that results do not collapse when scams are harder.

## Limitations

- Everything in part B is synthetic. Real UPI behaviour will be harder.
- The message model inside the demo was trained on simulated template messages. On real public smishing it catches 68% (83% on Indian-network messages) but flags 39% of real legitimate SMS when used alone (section A2), so treat the message signal as unvalidated. Real legitimate bank and UPI notifications were not available to test false alarms.
- IEEE-CIS features are anonymized, so the readable reasons come from the simulator's interpretable features.
- The hard-mode validation set has only 94 scams, and some per-family test counts are small.
- The cost curve uses illustrative units, not real money.
- Not validated for privacy, fairness or safety. Not for real payment decisions.

## Roadmap

1. Train the message model on real smishing plus real legitimate payment and bank messages (none found in public data), then re-evaluate it inside the full system.
2. Fine-tune a small transformer for message classification and compare it with TF-IDF.
3. Compare a graph neural network with the engineered receiver-network features.

## Run it

```
pip install -r requirements.txt
python orion3_sim_v3.py        # simulator + full evaluation (easy and hard mode)
python ieee_cis_benchmark.py --data path/to/train_transaction.csv --out results   # real-data benchmark
python text_real_eval.py       # message models on real public smishing (downloads the data)
streamlit run app.py           # demo app (trains the models on first start)

pip install fastapi uvicorn requests
uvicorn api:app --port 8000    # API; open http://localhost:8000/docs
python bench_api.py            # measures round-trip time over 300 requests
```
